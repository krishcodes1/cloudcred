03 — Database Design
CREATE TABLE
with constraints.
USERS Users table with constraints 
CREATE TABLE Users (
  user_id        SERIAL PRIMARY KEY,
  email          VARCHAR(255) NOT NULL UNIQUE,
  password_hash  VARCHAR(255) NOT NULL,
  full_name      VARCHAR(100) NOT NULL,
  created_at     TIMESTAMP DEFAULT NOW(),
  is_premium     BOOLEAN DEFAULT FALSE,
  CHECK (email LIKE '%@%.%')
);
SERIAL auto-increments user_id. UNIQUE blocks duplicate emails. CHECK validates email format at insert — bad data never reaches the table.
Normalization

1NF → 2NF → 3NF

  • 1NF — all columns atomic
  • 2NF — institution_name moved out
  • 3NF — no transitive dependencies

05 — SQL Demonstrations · 1 of 4
Aggregation &
grouping.
Q1 Monthly spending by category 
SELECT c.category_name,
       SUM(t.amount) AS total,
       COUNT(*)      AS txn_count
FROM Transactions t
JOIN Categories c
  ON t.category_id = c.category_id
WHERE t.txn_date >=
      DATE_TRUNC('month', NOW())
GROUP BY c.category_name
ORDER BY total DESC;
Joins Transactions to Categories, filters to this month with DATE_TRUNC, then totals each category. The dashboard pie chart reads this directly.
Q2 Utilization buckets with CASE 
SELECT
  CASE
    WHEN bal/lim >= 0.70
      THEN 'CRITICAL'
    WHEN bal/lim >= 0.30
      THEN 'HIGH'
    WHEN bal/lim >= 0.10
      THEN 'MODERATE'
    ELSE 'HEALTHY'
  END AS bucket,
  COUNT(*) AS n
FROM CreditCards
GROUP BY bucket;
CASE WHEN turns numeric utilization into four labeled buckets, then we count cards per bucket — powers the credit-health pie chart.
Also used: HAVING · DISTINCT · BETWEEN · LIKE08 / 19

Joins &
subqueries.
Q3 Largest transactions per user 
SELECT u.full_name,
       cc.card_name,
       t.merchant,
       t.amount,
       t.txn_date
FROM Transactions t
JOIN CreditCards cc
  ON t.card_id = cc.card_id
JOIN Users u
  ON cc.user_id = u.user_id
WHERE t.amount > 200
ORDER BY t.amount DESC
LIMIT 10;
3-way JOIN across Transactions → CreditCards → Users to get the top 10 largest purchases over $200, with full context.
Q4 Self-join: parent to child category 
SELECT
  p.category_name AS parent,
  c.category_name AS sub,
  COUNT(t.txn_id) AS n
FROM Categories p
JOIN Categories c
  ON c.parent_id = p.category_id
LEFT JOIN Transactions t
  ON t.category_id = c.category_id
GROUP BY p.category_name,
         c.category_name
ORDER BY parent, n DESC;
Self-join — Categories joins to itself so each parent (Food & Dining) groups its subcategories (Restaurants, Groceries, Coffee).

CTEs & window
functions.
Q5 Monthly trend with running total 
SELECT
  TO_CHAR(txn_date, 'YYYY-MM')
    AS month,
  SUM(amount) AS total,
  SUM(SUM(amount)) OVER (
    ORDER BY
      TO_CHAR(txn_date, 'YYYY-MM')
  ) AS running_total
FROM Transactions
GROUP BY month
ORDER BY month;
Window function — SUM() OVER (ORDER BY month) gives a running total without a self-join. One pass, sorted output.
Q6 Rank cards by utilization 
SELECT user_id, card_name,
  ROUND(
    current_bal/credit_limit*100,
    1) AS util_pct,
  RANK() OVER (
    PARTITION BY user_id
    ORDER BY current_bal/credit_limit
    DESC) AS user_rank,
  DENSE_RANK() OVER (
    ORDER BY current_bal/credit_limit
    DESC) AS overall_rank
FROM CreditCards;
RANK + PARTITION BY — ranks each user’s cards against their own, plus a global rank across all users. Two rankings in one pass.

05 — SQL Demonstrations · 4 of 4
Mutations &
transactions.
Q7 Flag overdue cards 
UPDATE CreditCards
SET is_overdue = TRUE
WHERE due_date < CURRENT_DATE
  AND current_bal > 0
  AND is_overdue = FALSE;

-- Runs nightly via Supabase cron.
-- iOS sees the badge on next sync.
Single UPDATE flips overdue cards in one statement. Supabase cron runs it nightly — no app-level loop needed.
Q8 Open a dispute inside a transaction 
START TRANSACTION;

INSERT INTO Disputes
  (txn_id, user_id, reason, status)
VALUES
  (4812, 1, 'Charged twice',
   'OPEN');

UPDATE Transactions
  SET is_disputed = TRUE
  WHERE txn_id = 4812;

COMMIT;

-- ACID: both land or neither does.
BEGIN/COMMIT wraps two statements as one atomic unit. If either fails, ROLLBACK — the disputed flag never sets without a matching dispute row.

06 — Views
Reusable query
surfaces.
Views let iOS read dashboard data in a single SELECT instead of joining client-side. We ship 4 views; two shown.
V1 v_user_dashboard 
CREATE VIEW v_user_dashboard AS
SELECT u.user_id, u.full_name,
  COUNT(DISTINCT cc.card_id)
    AS card_count,
  COALESCE(SUM(cc.current_bal), 0)
    AS total_debt,
  ROUND(SUM(cc.current_bal) /
    NULLIF(SUM(cc.credit_limit),0)
    * 100, 1) AS util_pct
FROM Users u
LEFT JOIN CreditCards cc
  ON cc.user_id = u.user_id
GROUP BY u.user_id;
Bundles every dashboard aggregation into one view. iOS just runs SELECT * FROM v_user_dashboard WHERE user_id = ?.
V2 v_upcoming_payments 
CREATE VIEW v_upcoming_payments AS
SELECT
  cc.user_id,
  cc.card_name,
  cc.due_date,
  cc.current_bal,
  ROUND(cc.current_bal/cc.credit_limit
    * 100, 1) AS util_pct,
  (cc.due_date - CURRENT_DATE)
    AS days_until_due
FROM CreditCards cc
WHERE cc.due_date BETWEEN CURRENT_DATE
  AND CURRENT_DATE +
      INTERVAL '14 days';
Postgres date arithmetic — (due_date - CURRENT_DATE) returns days as an integer. Powers the Payments screen with zero client-side math.

07 — Procedures & Triggers
Server-side
logic.
PROC get_user_summary() 
CREATE FUNCTION
  get_user_summary(p_user_id INT)
RETURNS SETOF v_user_dashboard
LANGUAGE sql AS $$
  SELECT *
  FROM v_user_dashboard
  WHERE user_id = p_user_id;
$$;

-- iOS calls on app launch:
-- SELECT * FROM
--   get_user_summary(1);
Postgres function wraps the dashboard view behind a callable name. iOS makes one API call on launch instead of joining four tables.
TRIG trg_flag_high_util 
CREATE FUNCTION flag_high_util()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.current_bal /
     NEW.credit_limit > 0.90 THEN
    INSERT INTO Alerts
      (user_id, alert_type, message)
    VALUES (NEW.user_id,
      'HIGH_UTIL',
      'Card over 90% utilization');
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_flag_high_util
  BEFORE UPDATE ON CreditCards
  FOR EACH ROW
  EXECUTE FUNCTION flag_high_util();
BEFORE UPDATE trigger auto-inserts an alert when utilization crosses 90%. The database itself is the source of truth — no app polling.

IDX Index strategy 
CREATE INDEX idx_txn_card_date
  ON Transactions(card_id, txn_date DESC);

CREATE INDEX idx_txn_category
  ON Transactions(category_id);

CREATE INDEX idx_txn_merchant
  ON Transactions(merchant);

CREATE INDEX idx_card_user
  ON CreditCards(user_id);

CREATE INDEX idx_card_due
  ON CreditCards(due_date);

CREATE UNIQUE INDEX idx_user_email
  ON Users(email);

-- Composite for dashboard query
CREATE INDEX idx_txn_user_month
  ON Transactions(card_id, txn_date);
Six targeted indexes. The composite (card_id, txn_date DESC) is the workhorse — the dashboard’s most common query reads pre-sorted rows directly.

12 — Conclusions
What we learned
& what's next.
What we learned
  • 3NF normalization paid off — no anomalies across 847 transactions
  • Composite indexes on (card_id, txn_date) cut dashboard load 342 ms to 38 ms
  • Views and procedures drastically simplified iOS client code
  • Triggers caught 100% of high-util events without polling
  • Parameterized queries are non-negotiable
Future work
  • Partition Transactions by month for multi-year scale
  • Full-text MATCH AGAINST on merchant + notes
  • Materialize v_monthly_spending for sub-10 ms analytics
  • Migrate AI context to a read replica
  • Row-level encryption on sensitive PII columns
